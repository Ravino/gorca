## 1. `AtspiDocSource` (`crates/gorca-doc-source-atspi`)

### 1.1 Where it lives and what it talks to

A new crate, not `gorca-connector-atspi`, for three reasons: the connector is being changed by other work (M1/M2), the source needs
no `atspi` types (it speaks raw D-Bus to the browser's own socket), and the web mirror should not have to import the connector.
The connector's Phase-0 `AtspiDocSource` stub stays until the daemon wires the new one. `xtask` rules were amended accordingly:
the crate and the harness may use `zbus`; `gorca-core` may not depend on any `gorca-doc-source-*` except `-api`; the bench crates
may read the environment, the source may not (`ConnectOpts::runtime_dir` is a parameter). One additive change in
`gorca-dbus`: `call_method_to` (destination optional, for peer-to-peer connections).

Modules: `p2p` (pool of N connections to the app's socket, address validated: `unix:path=` below the runtime dir, a real socket
owned by the runtime dir's uid; fallback to the bus connection), `wire` (hand-written readers, below), `fetch` (block fetch),
`warm` (cache domains), `identity` (ladder C), `events` (event normalisation, dirty set, settle), `source` (the `DocSource`),
`bus` (event feed for the harness), `roles` (AT-SPI role/state numbers read from at-spi2-core, mapped to `gorca_model`).

### 1.2 Block fetch [live]

`Collection.GetTree(rule, [Name, ChildCount, Attributes])` returns a flat DFS list; role and state are methods, not
properties, so they are separate pipelined passes. The strategy that won:

1. **Frontier split.** `GetChildren` expands the top of the tree (up to 16 subtrees or 4 levels), then one `GetTree` per frontier
   subtree is spread over the lanes. Total time equals one `GetTree` on the root (1.54 s for both at 100k) but the longest call
   the browser's main thread serves for us drops from **494 ms to 5 ms** (10k: 42 ms to 0.5 ms). That is the jank bound
   (WM-9) at no cost. A page with one giant leaf container is not bounded by this (open risk, section 6).
2. **Tiers.** `GetRole` for every node; `GetState` only for roles where state matters (buttons, links, form controls, list items,
   cells...; others get showing+visible+enabled): 100k nodes 1.54 s, against 2.17 s with `GetState` for all and 1.32 s with none.
   Text (`Text.GetText(0,-1)` per text-bearing node) is a third tier: +1.1 s at 100k, off by default.
3. **Window 32 in flight per connection, 4 connections.** w8 1.86 s, w16 1.83 s, w32 1.54 s, w64 1.93 s, w128 1.90 s (100k).
   Connections: the server is the browser main thread, so 2 is enough (table in section 2).
4. **Decoding is not a cost.** A hand-written byte reader (zvariant `Value`s would allocate several times per property) decodes
   22 MB / 102k nodes in 31 ms single-threaded; large replies go to the blocking pool.
5. **Reconstruction check.** The tree is rebuilt from DFS order and `ChildCount`; a node over `ATSPI_MAX_CHILDREN` (65,536) or
   a `MANAGES_DESCENDANTS` node breaks the arithmetic, which is detected (`Shape` error) rather than repaired. The fallback walk
   of AS-2 is not implemented (section 6).

Cost constants for the planner (TBD-B6-5): per node, `GetTree` ~4.9 us, `GetRole` ~6.2 us, `GetState` ~6 us, all pipelined and
browser-bound; a single synchronous call costs ~150 us latency. These replace the ADR's initial `alpha ~ 12 us`, `beta ~ 30 us`.

### 1.3 Cache domains are not optional [live]

The first mirror of a page lacked `tag` on the nodes it read before Firefox's Attributes domain was active (found by the
mirror-versus-fresh-fetch check: the first link had no `tag`). AS-3 is now implemented and verified (`warm.rs`): five throwaway queries on the
document root, then `GetTree` of the first, middle and last top-level child until the tagged-node count is non-zero and equal
in two consecutive probes. It runs once per application connection.

The cost is the interesting part. Activation is done by the **content process**, which re-sends the attribute data of
every node: **~25 us per node** plus a fixed ~30 ms (1k page 60 ms, 10k 272 ms, 100k 2.38 s). That is the whole difference between the cold and the warm first block:

| page | cold first block (warm-up inside) | first block, domains already active | first block after pre-warming on another document, then navigating |
|---|---|---|---|
| 1k | 71 ms | 9 ms | 14 ms |
| 10k | 282 ms | 10.7 ms | 22 ms |
| 100k | 2,459 ms | 80 ms | 187 ms |

Activation is per application, not per document (`prewarm` scenario: warm on a tiny first page, navigate the same tab to the page
under test: no warm-up left). **gorca must warm the domains when it attaches to Firefox, before any page it cares about is loaded.**
If gorca starts after a 100k-node page, the first read of that page pays 2.4 s once. The first *full* build of a never-queried page also pays
~1 s of lazy ATK object creation (100k: 2.6 s first, 1.5 s afterwards).

### 1.4 Progressive build (viewport first)

`fetch_first_block` expands the top, fetches leading subtrees until 400 nodes are complete (roles and states included) and the
source pushes that block with `Reset`; the rest follows as a second block. `Children` lists of the interior nodes are complete
and name ids whose `Upsert` is still to come. With the domains active the first block is ready in 10.7 ms (10k) and 80 ms
(100k), inside the ADR budgets (150 ms / 300 ms). The block size is a parameter (`first_nodes`).

### 1.5 Incremental updates [live, unit]

Events (`ChildrenChanged`, name/description/value, state, text, defunct; `/system` suffix and index -1 normalised) go into a dirty
set (O(1) per event, bounded by distinct nodes) which settles after 25 ms of quiet (cap 120 ms; **1 s for a burst with at
least 50 `ChildRemoved`**, see 1.6). Then the source re-reads what changed and nothing else:

* children of a dirty parent: one `GetChildren`; only paths the mirror does not know are fetched (`GetTree` per new subtree,
  one shared role/state pass); the identity ladder decides which new object continues which old item; the output is `Upsert`s,
  complete `Children` lists and `Removed` for items that continue nowhere;
* name/state events: four calls per node, in parallel with a window;
* text events: `GetText` when the text tier is on;
* more than 400 distinct dirty nodes: resync (whole document re-fetched and re-matched with the ladder, ids survive; only a
  new root object resets);
* the document root going defunct, or three failed root listings, ends the source with `Detached` (IR-7).

The same loop answers the doc actor's pull requests: `Subtree`, `Text`, `Action` (focus, click, scroll, caret, selection),
`Validate` (role unchanged), and the new `Revalidate{parent}` (IL-R1: one `GetChildren`, deltas for the difference, reply with
the current ordered child ids). Chromium reorders a keyed list without any event (section 4.1); **`Revalidate` repaired 100 % of
those cases** (churn: `reverse` and `shuffle`, 0 events, mirror wrong, after `Revalidate` equal to a fresh fetch, ids unchanged).

Every IPC call has a deadline (update calls 300 ms; block-fetch calls 5 s inside a 20 s budget with a per-pass cut-off; address and connect 500 ms each); a hung node costs its own call only
(test: one `GetRole` that never answers, fetch returns in 150 ms with exactly one failed call). The sink never blocks.

### 1.6 Identity, variant C, as implemented and what the measurements changed

The ladder of ADR-0003 section 5.1 works on `SrcNodeId`s inside the source: an object the page re-created keeps the id of the
logical item, so the mirror sees an in-place `Upsert`. Findings that changed the rules (all in ADR section 5.1 now):

1. **A changed signature is an edit, not a rewrite.** Item names are computed from content (renaming a button renames its `li`),
   so "two siblings changed" fired on every edit and re-fetched the whole list. The rewrite test is now *permutation*: the
   new signatures of at least two changed siblings are old signatures of other siblings.
2. **IL-3b only inside gaps between anchors.** Pairing leftovers by `(role, tag)` over the whole list handed the id of a row that
   scrolled out at the top to a row that entered at the bottom.
3. **IL-R6, ids of existing objects are never fresh.** Chromium keeps the old `id` attribute after an attribute-only change. A resync after an
   in-place rewrite matched through the stale ids and followed the object, not the content.
4. **IL-R7, moves in progress.** Firefox delivers a 2,000-row DOM move as 4,084 events over >100 ms. A refresh at the 120 ms cap
   saw the rows as gone and then as new: 650 of 2,045 ids lost on a reverse, 2,003 on a shuffle. A burst with >= 50 removes now
   waits for quiet up to 1 s; the result is 2,045 of 2,045, one update, 380-410 ms. The mirror-side re-match window of IL-R4 is
   still the second line of defence and belongs to the doc actor.
5. **IL-R5, resync keeps ids.** 20,308 events from an in-place rewrite of 2,000 rows: one resync of 4,073 nodes, 535-605 ms, 2,035 of 2,035 ids follow their content.

### 1.7 The neutral format (`gorca-doc-source-api`)

`DocDelta` stays the contract (the real `gorca_doc::DocumentMirror` ingests our deltas without a single `UnknownNode`: unit test).
Added to the API crate, nothing to `gorca-model`: `web_attrs` (well-known `AttrKey`s for `tag`, DOM `id`, `class`, `xml-roles`,
`level`, live attributes, `posinset`, `setsize`, grid indices, raw role), `TreeBlock` + `Completeness` (a document-ordered block that
chunks into `Reset`/`Upsert`/`Children` deltas), and `DocRequest::Revalidate`. The conventions a consumer may rely on are in the module
doc of `web.rs`: blocks and unfetched ids, order inside a batch, `Upsert` replaces `text` wholesale, ids are logical.

## 3. The B-6 harness skeleton

`crates/gorca-bench-web` (binary `b6`) and `tests/web/b6` (README there). Pieces:

* **Corpus loader** (`corpus.tsv`): `gen_large` pages generated in Rust with the templates of `tests/web/pages/gen_large.py` (1k, 10k, 100k),
  the SPA list (200 and 2,000 rows) with vanilla DOM operations that give the same AT-SPI streams as the framework apps,
  windowed lists (unmount, recycle, grid), real virtual-scroll libraries (`virt/`: TanStack Virtual, vue-virtual-scroller, Angular CDK, built with
  esbuild into gitignored bundles), the existing frames/shadow/canvas page, a warm-up page. SPA framework apps stay in `tests/web/spa` and are listed as optional.
* **Private browser** (`firefox.rs`, `run_b6.sh`): own dbus + a11y bus + registryd + headless gnome-shell on a unique Wayland display, Firefox with `--no-remote
  --new-instance --profile <tmp>` (`accessibility.force_disabled=0`, `GNOME_ACCESSIBILITY=1`, no proxy, no telemetry), one browser per (page, scenario); Chromium headless=new
  with `--force-renderer-accessibility`. `b6 run` refuses to start under a `/run/user/` runtime dir or on the live a11y bus; teardown signals only the
  process group the harness started.
* **Page channel** (`server.rs`, `driver.js`): the page long-polls the harness for commands and acknowledges them with its own epoch timestamps (no Marionette, no CDP), so DOM
  mutation times are exact on the same clock as the harness.
* **Scenarios**: `build` (M-9 / WM-1, strategy matrix, stage times, first block cold and warm), `churn` and `churn-nodomid` (WM-4 and M-13, with a consistency check of the mirror against
  a fresh fetch after every step and `Revalidate` repair), `scale` (M-15), `research` (TBD-WEB), `prewarm`.
* **Arms** (`arm.rs`): `B6Arm` with `build` and `attach`. `AtspiTunedArm` is arm (a). `AgpFirefoxArm` is the arm (b) skeleton: it lists what the bootstrap
  (`browser/firefox-agp/`), the client crate and the lockstep aligner must provide and returns `NotImplemented`, so a B-6 run cannot measure arm (a) twice.
  Both share the corpus, the oracle mirror and the scenarios; arm (b) only has to produce a `Session`.
* **Metric names.** The task text names M-9, M-13 and M-15 as build time, update latency and identity stability. In the ADRs M-9 is the build, M-13 identity, M-15 parallel scaling, and update latency is
  WM-4. The harness reports all four under those names.

Known gaps in the harness: no event-storm rate sweep (SRC metric 3: 1k/10k/50k events/s), no rAF jitter probe (in Firefox the a11y queries are served by the parent process, so a page-side probe does not see
them; `heaviest_get_tree_call` is the proxy), no browser CPU accounting from `/proc`, and the Chromium DOM-id ground truth is unavailable for in-place attribute rewrites (the attribute is stale), so the
`rewrite in place` step is only valid for Firefox; Chromium identity under recycling is covered by the content-labelled research pages.

## 4. TBD-WEB-1/2/3 [live]

Method: `research` scenario. Before and after each scroll or reorder step a snapshot with `GetState` of every node is taken and compared for nodes that exist in both
(by object path); every object event of the step is counted; rows carry `aria-label="Row i"` as ground truth for identity. Seven windowed pages per browser: hand-written list (unmount,
recycle, grid), TanStack Virtual under React 19 (rows keyed by index; rows keyed by pool slot), vue-virtual-scroller `RecycleScroller`, Angular CDK `cdkVirtualFor` (template cache 20), plus the SPA list and the 10k page for
window scroll. 42 scroll steps per browser on the windowed pages.

### 4.1 TBD-WEB-1: which states flip on scroll or reorder, and with which events

**Only `showing` flips, in both browsers, and nothing announces it.**

| | Firefox 153 ESR | Chromium 153 |
|---|---|---|
| nodes whose `showing` changed, windowed pages (persisting nodes compared) | 109 of 895 over 42 steps | 296 of 1,668 over 42 steps |
| per 2-row scroll step | 4 (list), 16 (grid) | 7 (list), 24 (grid), 12 (TanStack) |
| window scroll, 411-node SPA page / 10k page | 63 / 65-68 per step | 93 / 131-140 per step |
| `visible`, `focused`, any other bit | never changed | never changed |
| `StateChanged` events for those flips | **0** | **0** |
| keyed reorder (reverse, shuffle) | remove + add events, objects re-created | **no event of any kind**, paths stay, order changes, 144 `showing` flips |

Chromium's source agrees: `SHOWING` is computed as visible and not offscreen and not minimized (`ui/accessibility/platform/ax_platform_node_auralinux.cc:3145-3149`), and `OnShowingStateChanged` is only reached for menu popups.
Consequences for the mirror: `showing` is viewport state; it must not be cached or used for the `cats` hidden filter (use `visible`), it can be read live when needed, and Chromium's silent reorders are detected only by
`Revalidate`. A related observation: after a route swap the Chromium document name (`document.title`) did not change in the mirror within the 700 ms quiet window (no `PropertyChange` on the document), so the title is not a reliable route-swap
signal there.

| | Firefox | Chromium |
|---|---|---|

### 4.3 TBD-WEB-3: identity retention under scroll with DOM-recycling virtualisers

A row that stays visible across a step (name present before and after):

| page / library | Firefox: retained, same path, same logical id | Chromium: retained, same path, same logical id |
|---|---|---|
| hand-written unmount / recycle / grid | 17 / 20 / 17 of the same | 17 / 20 / 17, all identical |
| TanStack Virtual, index keys | 16 / 16 / 16 | 22 / 16 / 20 |
| TanStack Virtual, pool-slot keys | 16 / 16 / 16 | 22 / 16 / 19 |
| vue-virtual-scroller | 140 / 140 / 140 | 140 / 140 / 134 |
| Angular CDK | 20 / 20 / 20 | 20 / 20 / 20 |
| total | **246 / 246 / 246 (100 %)** | **258 / 246 / 247 (95.7 %)** |

Wrong node (an id carrying another item's content while that content exists elsewhere): **0 in 84 steps**. The 11 Chromium retained rows that lost their id are rows that moved to another object in the React pool
(path differs) and the steps in which Chromium changed the page silently (vue-virtual-scroller: mirror unequal to the page in 2 of 42 steps, no event; `Revalidate` is the repair).
What the libraries do to the AT-SPI tree: mount/unmount disciplines (react keyed by index, CDK) produce only child add/remove for entering and leaving rows; recycling disciplines (pool-slot keys, RecycleScroller, hand-written pool)
also overwrite objects in place (`name-changed` 14-40 per step), after which the entering row sits on the leaving row's object. A jump longer than the window retains nothing, and the ladder then pairs leaving and entering rows by position only when
no anchor exists (606 Firefox / 635 Chromium such heuristic reassignments, all flagged as `by_role_tag` joins, none with strong evidence against). Decision for M7: a bookmark on a row that scrolled out of a virtualised list must fall back to
the text anchor / `aria-posinset`, not rely on the logical id surviving a jump.

## 6. Risks and what is not verified

* **Giant leaf containers.** The frontier split bounds a `GetTree` call by the largest frontier subtree; a page with one container holding 100k nodes still blocks the browser's main thread for ~500 ms in one call.
  `GetChildren` fails above 65,536 children and the `GetTree` reconstruction breaks there; the fallback walk (AS-2) with `GetChildAtIndex` is not built. The corpus has no wide (50k siblings) or deep (500) page yet.
* **Events during the build** wait in a bounded channel (the harness uses 65,536); an overflow loses events and the source does not yet resync on it (the bus listener counts drops).
* **Event-storm rates** (1k / 10k / 50k events/s, SRC metric 3) were not swept; the largest burst measured is 20,308 events delivered over ~100 ms and handled by one resync.
* **Text** is read raw (`GetText(0,-1)`); Firefox hypertext (U+FFFC per child, UTF-16 with BOM) is not turned into text-leaf nodes (TX-1 stays with the connector/doc layer), and the text tier is off by default.
* **Coverage matrix** (cross-site iframes, closed shadow, canvas, PDF.js, `aria-owns`) is in the corpus (`frames-outer`) but was not run; it needs the second origin server.
* **Chromium identity ground truth.** Chromium keeps a stale `id` attribute after an in-place attribute change, which also makes the DOM-id ground truth of the churn scenario meaningless for the
  `rewrite in place` step; the content-labelled research pages cover Chromium. Chromium also drops the document name update on `document.title` changes within the quiet window.
* **One host, one ESR.** Firefox 153.4 ESR and Chrome for Testing 153 only; no ESR-N+1/release run; the host was shared (load average 4-10), so absolute numbers carry ~10 % noise.
* **Firefox lazy object creation.** The first full build of a never-queried page costs ~1 s more at 100k nodes (2.6 s versus 1.5 s afterwards); not on the first-block path.
* **P2P** worked for Firefox and, new, for Chromium (headless=new): `GetApplicationBusAddress` returned a socket in the private runtime dir, so P-9's "Chromium P2P expected yes, not observed" is now observed. Flatpak/Snap (TBD-WEB-4) is untested.
* Arm (b) is a skeleton; the B-6 rule (5x on metrics 1-3, then robustness, coverage, cost) cannot be evaluated until it exists. For reference, arm (a) is already at 1.5 s / 100k, 29 ms for one node and 10 ms to a speakable block, so 5x would need 0.3 s / 6 ms / 2 ms.
