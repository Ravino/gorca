## Findings (ranked)

### F1 High: a modifier grab is changed while the modifier is held after pass-next-key
`crates/gorca-input-mutter/src/source.rs:509-510` (`track_held`) records a held modifier only if it is in the
grab set at the moment of the press. In `PassThrough{OneKey}` the grab set is empty
(`docs/design/modes.md` §3), so the modifier press is not tracked.
Scenario: the user presses Insert+F2 to send the next chord to the application, as the spec intends ("send the next key or chord").
Then the user presses Insert+T. The Insert press reaches the app and is not tracked. The T press ends pass-through
(`handlers.rs:468`), and the Reader asks for {Insert} again while Insert is still down. `modifiers_change` is true and
`held` is empty, so the set is sent at once (`source.rs:449-457`). This is the P-7 hazard (measurement report, "Hazard found"):
the release is swallowed as a first click, so the app and XKB never see Insert come up. Insert stays down in the
client (client-side autorepeat). With Caps Lock as the modifier, Caps Lock gets stuck, which breaks the "Caps Lock state unchanged" requirement.
Fix: track presses of every keysym that is or may become a gorca modifier (committed ∪ wanted ∪ `keymap.modifiers`),
not only the ones grabbed now. Add a source-level test (pass-through, modifier down, restore request, so the send is deferred) and a
fake_mutter case.

### F2 High: concurrent `SendGrabs` tasks can reorder and leave the keyboard fully grabbed
`monitor.rs:380-399`: `SetGrabSet` while `Pending` emits a new `SendGrabs` immediately. `source.rs:585` spawns
each one as an independent task on the multi-threaded runtime (`gorca-daemon/src/lib.rs:83`). Each task makes two
dependent calls: `SetKeyGrabs`, then `GrabKeyboard` or `UngrabKeyboard` (`source.rs:600-615`). Nothing orders task A's second call against task B's.
Scenario: Mutter stalls (the case the 200 ms deadline exists for) while learn mode is toggled on and then off, or while
HelpStall and the Reader's own exit both publish a set. Both `SetKeyGrabs` replies arrive together and the tasks wake on two
workers. The wire order becomes A.Set, B.Set, B.Ungrab, A.Grab. Mutter now holds the whole keyboard while the FSM says `Committed` normal.
Every key is swallowed until the next grab change: a dead keyboard for a blind user. A late, superseded `SetKeyGrabs` can also land after the
newer one, which leaves stale grabs.
Status: found by code inspection, not reproduced (fake_mutter adds no latency). Fix: keep one grab writer per
connection. Allow at most one set in flight and coalesce the newest wanted set until the reply, or issue both calls
back-to-back from the session task so the wire order follows FSM order.

### F3 Medium: `InputLane::reset()` is never called; stale lane state after a monitor loss
`lane.rs:130` has no caller (grep shows only its definition). After a shell restart, or any session end, with a key
down, `down` and the replica's `grabbed_keypresses` keep it. Reproduced by
`probes/audit_m1_lane.rs`: Insert down, restart (same grab generation 1), then a plain T is classified
`Command(window title)`, while real Mutter passes T to the app. Result: the command runs and "t" is also typed. This persists until
Insert is tapped. Fix: publish a session epoch in `GrabView` (or a `reset` flag on reconnect) and call `reset()` when it changes.

### F4 Medium: TOCTOU between `GetNameOwner` and the `NameOwnerChanged` subscription
`source.rs:288-331` resolves the manager's unique name before subscribing to its owner changes. If gnome-shell is replaced in that gap
(likely right after a `--replace`, when gorca reconnects 100 ms later), `WatchKeyboard` goes to the new owner
while `SenderFilter` keeps the old one. Every real `KeyEvent` is then dropped, and no owner-change signal ever arrives.
Commands are dead with no notice. `rejected` is counted but never logged.
Fix: subscribe first, then `GetNameOwner`, then `WatchKeyboard`, and restart if the owner stream yielded meanwhile. Log a rate-limited
warning when `rejected` grows.

### F5 Medium: hot reload ignores a revert to gorca's own saved text
`config_task.rs:224` skips a reload when `hash == own_hash`, and `own_hash` is never cleared. The sequence is
save (file Y), user edit (X, loaded), user reverts to Y. The revert is skipped, so the active settings stay X while the file says Y.
Reproduced: `probes/audit_m1_config.rs::reverting_to_our_own_saved_text_is_reloaded` fails. Fix: clear
`own_hash` after the first matching event, or compare only against `last_hash` and set `last_hash` on save (this is already done).
`own_hash` is then redundant.

### F6 Low: save replaces a symlinked `gorca.toml` with a regular file
`config_task.rs:159` writes `tmp` and renames it over the path. A dotfile-managed symlink is replaced, and the target keeps the old text.
Reproduced: `probes/audit_m1_config.rs::save_keeps_a_symlinked_settings_file` fails. File mode is not preserved, and
the directory is not fsynced. Fix: `canonicalize` the path before writing, and copy the permissions.

### F7 Low: save has a small read-check-rename race
`config_task.rs:270-310`: an editor write between the read in `save` and the `rename` is clobbered. The HR-5 hash
check covers edits the watcher has already seen. The window is milliseconds. Accept and document it, or re-stat (mtime and inode) just before `rename`.

### F8 Low: the M1 gate harness reads the ambient environment in unit tests
`gorca-bench/src/e2e/m1.rs:78` falls back to `std::env::var`. Exporting `GORCA_M1=1` therefore makes run.sh's
pre-flight unit tests fail, so the orchestrator's exact command cannot pass. Fix: tests pass explicit `HostEnv`, and the fallback
belongs only in `bin/e2e.rs`.

### F9 Low: physical keycode table (`StaticResolver`)
For the user's setup (us+ru, Super+Space, empty xkb-options) the risk is **nil for matching**. Chords match on
`KeyEvent.keycode` (`lane.rs`, `KeyRef::Code`), which is layout-independent. Modifiers match on keysym (Insert and Caps_Lock are
identical in us and ru), and P-15 shows that `KeyEvent.state` carries no group bits that could perturb the chord mask. The residual risks are:
(a) non-US physical layouts (de/fr) get US positions, and names in learn mode or in diagnostics are wrong; (b) TOML written with
Cyrillic key names is reported as an unknown key (a diagnostic, not a failure). Follow-up: build an XKB resolver from
RMLVO group 0 (as P-15 validated) before shipping to non-US users.

### F10 Low: coverage gaps
* The forger (`tests/harness/key_forger.py`) covers unicast `KeyEvent` forgery to the reader's unique name, before
  and after a manager restart. The negative control exists (`bench/results/e2e/m1-neg`, forged_accepted = 1 at 4d35e0f).
  Forged unicast `NameOwnerChanged` and forged chords (Insert+X) are not exercised.
* No e2e check of a double-tap pass-through or Caps Lock as the modifier (unit tests only, `mutter_model.rs:226+`).
* A panic in a `SendGrabs` task is swallowed (`source.rs:470`), which leaves `Pending` until the next set arrives.
* UX note for the checklist: double or triple where-am-I requires Insert to stay held. Releasing and re-pressing Insert within
  500 ms is a Mutter double-tap (`multi_press_ms` = `repeat_delay` = 500), and then Tab moves focus.

## Checked and found correct
* MonitorState/GrabSetState: every (state, msg) pair is spelled out. Stale generations are ignored. Retries ×2 lead to `Lost` and a reconnect within ~1 s.
  Orca running: `RequestName(DO_NOT_QUEUE)` never displaces it; the notice is said once and the name is polled every 5 s.
* The sender check runs on every `KeyEvent` header against the resolved unique name, and is re-resolved on each session.
  `NameOwnerChanged` is accepted only from the bus daemon.
* Learn mode: everything except `speech.stop` and `input.learn_mode_toggle` (the only `input_help_bypass` commands) is `Described`.
  Plain Escape exits. LM-3 idle and stall nets are in the pump.
* Config: a malformed, binary, 200k-deep nested or oversize (>1 MiB) file reports diagnostics and never fails
  (`gorca config check`). The loader runs under `catch_unwind`, and the read has a 1 s deadline. Presets are built in (an enum, no paths), so
  there is no traversal surface. Saving with comments preserved is covered by `startup_hot_reload_explicit_reload_and_save`.
* Commands: multi-press counting on the lane (receipt time, `multi_press_ms`, capped by `max_press`), where-am-I
  1/2/3 = basic/detailed/spell, time/date, the voice ring sends levels before the confirmation, "speech off" is spoken before the mute,
  and autorepeat is debounced (120 ms, only `repeatable` commands).

## K4 at 10k switches: a harness design problem
In the quick run, 500 switches took 78 s (156 ms per switch). That is almost entirely fixed sleeps: `SETTLE_REAL_MS` = 40 ms
after each chord, after each pass-mode letter and at the end of each round, about 150 ms per switch. 10k switches therefore need at least 26 min of pure sleep,
and 50 min or more on a loaded host. The sleeps also make K4 blind to the interesting window: letters are typed only after the grabs have
settled, so neither the `Ambiguous` path nor F1 or F2 is ever exercised.

Faster equivalent:
1. **Event barrier instead of sleep.** fake_mutter exposes `wait_grabs(n)`, which returns once the n-th
   `SetKeyGrabs`/`(Un)GrabKeyboard` has been applied. The harness waits on it plus a 1 ms guard. Expected cost per switch is a few ms,
   so 10k switches take about 1 min.
2. **Race variant (K4r).** The same random walk with no wait: letters are injected 0–3 ms after the chord, and the result is scored on Mutter's ground truth
   (`consumed`, app log). Gate: lost = doubled = 0, and a lane `Command` never coincides with an app-delivered key.
3. **In-process property test.** Drive `InputLane` + `MonitorState` + `Replica` against a Rust port of fake_mutter's
   `first_click`/`should_grab`, with randomized keys, grab-set changes, reply delays and reorderings, at millions of steps per second.
   That covers the statistical 10k+ requirement. The e2e K4 stays at 500–1000 switches as a wiring check.
