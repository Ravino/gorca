## Findings (ranked)

### F-1 HIGH: with Num Lock on, the numpad no longer types digits in any application
`crates/gorca-core/src/commands/compile.rs:257-265` registers, for every keypad review chord, the Num Lock-on
pair: plain `KP7` becomes the exact grab `(KP_7, Mod2)`, `KP8` `(KP_8, Mod2)`, and so on, and `Shift+KP7` becomes
`(KP_Home, Shift|Mod2)`. The lane strips `Mod2` (`Modifiers::LOCKS`, `event.rs:28`) and looks up by keycode, so
each of those presses runs a review command. The branch pins this behaviour in its own test,
`desktop_keypad_review_keys_are_grabbed_with_the_keysym_each_num_lock_state_produces` (`assert!(has(&exact, KP_7, Modifiers::MOD2))`).

- **Failure scenario:** a user with Num Lock on (GNOME can restore it at login) types `7` on the numpad in a
  spreadsheet, a terminal or a password field. Gorca swallows it and says the previous review line. The digits
  1 to 9 and the decimal key never reach the application while gorca runs. `Shift+KP7` with Num Lock on (Home in a
  text field) is swallowed too.
- **It contradicts accepted rules:** ADR-0005 K-6a ("registered without the Num Lock variants: with Num Lock on
  the keypad types digits into the app, as in NVDA and Orca"), ADR-0006 KM-2 (unchanged), and modes.md §4.3
  ("unmodified keypad keys with Num Lock off"). The rewritten KM-3 and `docs/plan/checklists/M4a.md` ("with Num
  Lock on the keypad review keys steal the digits, as NVDA's do") contradict them. The NVDA claim is wrong: NVDA's
  desktop layout uses the numpad only with Num Lock off. Even the operator branch of the same function says
  "K-6a still leaves the Num Lock-on states alone".
- **Fix:** register only the Num Lock-off keysym, with and without `LOCK` (Caps). V-1 still matters: for `Shift+KP7`
  the keysym is `KP_Home` with Shift, not `KP_7`. Drop the `Mod2` pairs, flip the test assertions, and restore KM-3,
  the checklist and the decisions.md line to K-6a. If digit-stealing is ever wanted, make it an opt-in setting
  decided in an ADR.

### F-2 MEDIUM: one object step can wait about 480 ms; OB-3/R4 says at most 125 ms
`review/commands.rs:372` (`settle`) gives every suspension a fresh `now + 120 ms + 40 ms` deadline, and a step may
suspend 3 times (`nav_suspensions = 3`). OB-3 says all three suspensions fit in one 120 ms Interactive deadline, and
R4 says "never > 120 ms + 5 ms".
- **Probe** `probe_ob3_one_step_can_wait_far_beyond_125ms`: a slow but healthy app answers each fetch just before
  its deadline, and the step speaks after **477 ms** over 3 suspensions.
- Queued commands each start with `attempts = 0`, so a queue of 8 behind a slow app can delay the last utterance by
  seconds.
- **Fix:** store the step's first deadline in `Pending` and carry it through resumes (`deadline = min(first, now+wait)`).
  Give the whole queue one budget, or degrade the queued steps with no new IPC once the first deadline has passed.

### F-3 MEDIUM: one key can produce two utterances, the stale one first; a lost timer leaves the op pending
- `review_command` calls `expire_late` first (`commands.rs:226`). If a pending operation is past its deadline, that
  call runs the old command degraded **and speaks it**, and then the new command speaks too. Both utterances carry
  the current epoch.
  **Probe** `probe_late_pending_and_new_key_both_speak`: `["Cancel button", "Cancel button"]` for one key.
  ADR-0006 4.3 says only the last command speaks, and ADR-0001 R-1 says superseded results are never spoken.
- This path becomes likely because of how `runtime.rs:945` and `runtime.rs:886` handle timers. The runtime keeps a
  single `timer = min(armed)` and clears it when it fires. If a focus-settle or pass-through timer fires first, the
  review deadline is never re-armed. The pending operation then lives until the next key, which hits the path
  above. (Code reading; not reproduced end to end.)
- **Fix:** in `expire_late`, called from `review_command`, drop the late operation silently, only counting it.
  Keep the timer as a set, or re-arm the earliest outstanding deadline after each `Timer`.

### F-4 MEDIUM: a stale flat-review line is spoken with no correction (RR-1 incomplete)
- `review_revalidated` (`commands.rs:1010-1030`) starts a background rebuild on `Changed { text_changed: true }`
  but speaks nothing. ADR-0006 RR-1 requires a short RV-1 follow-up when the spoken line's text changed. The §20
  "Not in M4a" list mentions only the object-speech RV-1, not this one.
  **Probe** `probe_rr1_text_change_is_not_corrected`: the Reader says nothing.
- V-4 says no toolkit reports scrolling. So after a scroll, every step until the TTL check speaks lines that are no
  longer on screen, and nothing ever tells the user.
- Related: `validity::snapshot_hash` hashes role, states, name, value and bounds, but not the zone text, although
  ADR §6.3 includes "text range+text". A text node's lines are therefore checked only through the `stale` flags.
  If any other fetch of that node clears them (for example a focus refetch after `TextChanged`), the model looks
  valid with old text. This is unverified end to end.
- **Fix:** speak the corrected line when the verdict says the spoken line changed (counted in M-6), or record this
  as an explicit M4a deviation in §20. Add a per-node hash of the lines to the checks.

### F-5 MEDIUM: RR-1 reports "changed" on unchanged text, so text surfaces rebuild every 2 s
- `maybe_revalidate` (`commands.rs:965`) sends each zone's `rect` as the probe. For a text zone that is the
  **line's** rectangle (`cluster.rs:159`), and `revalidate` (`build.rs:571`) compares it with the **node's**
  extents.
  **Probe** `probe_rr1_unchanged_text_node_reads_as_changed`: an unchanged app gets
  `Changed { text_changed: false }`. Every review step over text, once each 2 s TTL expires, therefore starts a full
  background rebuild (`dirty = None`, so all visible lines are fetched again).
- Also from code reading: the revalidation `clip` is `(-10000,-10000,20000,20000)`, while the build clips to the
  surface rectangle. `GetOffsetAtPoint(-10000,-10000)` cannot return the first visible offset, so in a scrolled
  text view the fresh lines start at offset 0, never equal the model's, and `text_changed` is always true.
  `clip` also falls back to a zero rectangle when no zone has a rect.
- **Fix:** probe with node bounds (keep `snap.bounds` per node in the model). Revalidate with the same clip as the
  build (the surface rect).

### F-6 LOW-MEDIUM: holding a review key moves one line
`CoreCmd::repeatable()` (`commands/spec.rs:104`) lists only voice settings, so the lane swallows autorepeat of the
review keys without running a command. ADR-0006 RS-3 and the RQ gate (held key at 30 Hz, the last position always
spoken) assume review keys repeat, as in NVDA. RQ is not implemented in the harness.
**Fix:** make line, word and char moves repeatable, and add RQ.

### F-7 LOW: model builds go one tree level per round, so deep surfaces stay truncated
`build_model` (`build.rs:368`) expands one level per round, with `MAX_ROUNDS = 10`, plus one continuation
(`runtime.rs`). A surface deeper than about 20 levels below its root ends `Truncated(Deadline)` for good on a static
window. The truncation is honest: "Bottom, more content not shown". RS and R1 use trees 3 levels deep. Real GTK4
depth is unverified; check it on the live checklist apps, or add a deep tree to R2.

### F-8 LOW (harness): R1 `lost` hides late samples and gives them to the wrong key
`m4.rs` series: a speech that arrives after the next key is counted against the next key, and the late key becomes
`lost` instead of a latency sample. The p99 therefore leaves out exactly the worst cases. **Fix:** attribute each
SPEAK by its text (the series alternates "Row 0 button" and "Row 1 button"). Report late keys as latency and keep
`lost` for keys whose text never arrives.

## Item 4: the unexplained R1 failure (lost=2, p99 3.0 ms at load 14)

**Cause: a harness artifact on top of a real latency excursion. No review command was dropped.** It was reproduced
with an instrumented harness that dumps every key and every speech record, at load 20.5 (10 extra busy loops,
recorded PIDs, killed afterwards). One repeat in ten had `lost=1` (`diag/lost-analysis.txt`):

```
key 905 next  t=0        (no speech in its window, 13.37 ms long)
key 906 prev  t=+13.37   S +6.12 "Row 1 button" | STOP +9.2 | S +9.2 "Row 0 button"
```

`Row 1 button` is key 905's answer, and it arrived **19.5 ms** after the key. The harness credited it to key 906 as
6.12 ms and counted key 905 as lost. Every one of the 1200 keys was spoken (1200 SPEAKs, 48 STOPs).
Owner-attributed maxima per repeat under that load were 3.2 to 19.5 ms (`diag/*.tsv`). At load about 9, 22 repeats
had `lost = 0` and a max of 1.2 ms. So the `m4a-final` result is host scheduling under load. It does breach
the 15 ms product goal on single samples, but it is not a review defect. The gate needs F-8 so that these samples
show up as latency.

## Items 5 to 7

- **5. Cold first step.** At head the e2e fake app (24 buttons, flat) measures `r2_cold_ms` 5.8 to 7.6 ms. The
  first build is bounded by `BUILD_FIRST` (120 ms soft) and the Reader's `BUILD_WAIT` (500 ms), so it cannot hang
  the reader. About 100 ms on the first key is acceptable for M4a, because R2 is not gated. Before M4b, add the R2
  gate (500-node window, 0.2 ms per call, depth > 10; see F-7).
- **6. Shared code (IC-24).** `EVENTED` gains `BOUNDS` (`app_actor.rs:48`). The IC-24 test, `b1_ic`, the IC/MA
  suites and the real-daemon invalidation suite pass in `make check`. L1 to L4 and K1 pass at head. The connector
  does not subscribe to `BoundsChanged`, so nothing on the live path changes yet. The shadow-mode allowlist gains
  only read-only methods (`Component.GetExtents`, `Collection.GetMatches`, `Text` reads). `ReviewApply` goes
  through `on_external_reply`, so the LR rules apply. No B-1 invariant regression found.
- **7. Code hygiene.** No `unwrap()` outside tests, every match is exhaustive (clippy
  `wildcard_enum_match_arm` passes), and there is no new `unsafe`. Review tasks are bounded (`REVIEW_TASKS_MAX = 32`,
  each request under a class deadline). `send` drops a result when the review queue (64) is full, but the pending
  operation still has its timer, which is subject to F-3.

## Input-lane interaction (item 1, the rest)

Pass-next-key leaves `exact` out of the PassThrough grab set (`mode.rs`), so the next key reaches the app natively.
InputHelp uses `grab_all`. The single writer sends `exact` through the same `to_wire`, and the reader re-sends only
on `keys.exact` change (`handlers.rs:456`). `GrabSet` equality includes `exact`. The double-tap rule is unchanged:
`cur_*` take `max_press = 3`, and the moves fall back to `(chord, 1)`. `R1.not_consumed = 0`: every keypad press was
grabbed with Num Lock off. No leak or stuck key was found besides F-1, which over-grabs rather than leaks.
